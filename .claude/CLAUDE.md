# Viral Monitor — 혼수 가전 바이럴 모니터링 하네스

온라인 혼수가전 **구매후기**를 조사·분석하여, **전국 백화점에 입점한 삼성스토어 vs LG전자 매장**의
바이럴(구매후기) 현황을 매장·지역 단위로 비교하고, **삼성스토어가 LG보다 혼수 판매를 늘릴 인사이트**를 찾는다.

## 목적 (2026-06 개정 — 백화점 입점 매장 중심으로 재정의)

1. **대상 = 전국 백화점 입점 삼성스토어 vs LG전자 매장**의 혼수가전 구매후기 비교.
   - 비교 단위: ①전국 ②지역별 백화점 ③백화점 내 삼성 vs LG. 다양한 시각으로 드릴다운.
2. **모니터링 후기 = 혼수가전 구매후기**. "웨딩가전·신혼가전·혼수가전·가전 졸업" 등 표현이 다양하나, 결국 **결혼하며 구매하는 가전 후기**를 가리킨다.
3. **백화점 입점 매장 외 데이터는 분석에 사용하지 않는다(보관만).** 삼성스토어 단독매장·대리점·하이마트·온라인몰 등은 census에 보관하되 본 분석/대시보드 집계에서는 제외.
4. 목표 = LG 대비 우위·열세 진단 → **삼성스토어 혼수 판매 증대 인사이트** 도출.

## 백화점 매장 명칭 규칙 (집계 핵심)

- 후기에서 매장은 **백화점명 + 브랜드** 조합으로 불린다.
  - 백화점: 롯데·신세계·현대·갤러리아·AK 등 (약칭 롯/신세/현/갤 포함). 예) 롯데백화점 잠실점 → **롯데잠실 / 롯잠실 / 롯본점(본점)**.
  - 브랜드: 삼성·삼·삼성스토어 / LG·엘지·엘·하이프라자·베스트샵.
  - 예) "롯데잠실 삼성", "롯잠실 엘지", "신세계 강남 LG", "현대 판교 삼".
- 매장 키 = **백화점지점 + 브랜드(삼성/LG)**. 같은 백화점 지점에서 삼성 후기 vs LG 후기를 비교한다.
- 백화점 단서가 없는 후기는 "백화점 미상"으로 분류(분석 제외, 보관).

## 공통 규칙

- **분석 범위 = 2단 구조(2026-06 재조정).** ①**전국·지역 = 전체 후기 대상**으로 센싱(백화점 포함 모든 유통). ②**지역에서 매장을 특정할 때만 백화점 입점(롯데·신세계·현대·갤러리아·AK) 삼성스토어 vs LG전자**로 비교 — 그래야 삼성 vs LG 구도가 성립. census 전량은 보관.
- 매장 키 = **백화점지점 × 브랜드(삼성/LG)**. 명칭 약칭(롯잠실·롯본점·신세 강남 등)도 정규화해 같은 지점으로 묶는다.
- 모든 산출물은 `artifacts/` 아래에 `YYYYMMDD-` 접두사로 저장. 전수 census = `artifacts/cafe-census.json`(백화점 외 포함 보관), 분석용 = 백화점 필터 적용분.
- 웹 검색 결과는 **출처 URL을 반드시 함께 기록**한다 (검증 가능성 확보).
- 백화점 단서가 불명확한 후기는 "백화점 미상"으로 분류(분석 제외, 버리지 않고 보관).
- 집계는 추정임을 명시한다. 표본은 전수가 아니므로 "표본 기준 추정치"로 표기. 제목기반 추정과 본문확정을 구분 표기.

## 후기의 주체는 고객이다 (2026-08-23 사용자 지적)

**후기는 고객이 쓴다. 우리가 쓰거나 만들거나 늘리는 것이 아니다.**
매니저(직원)가 할 수 있는 일은 **구매 고객이 후기를 쓰도록 요청·독려하는 것**뿐이다.

액션 문구를 쓸 때 주체를 틀리지 않는다:

| 쓰지 말 것 | 쓸 것 |
|---|---|
| 후기 절대량을 키우세요 | 구매 고객에게 **후기 작성을 요청**해 표본을 넓히세요 |
| 후기를 늘리는 것이 과제 | **후기 요청**을 습관화하는 것이 과제 |
| 좋은 후기 만들기 | 좋은 후기가 **나오려면** |
| 후기 확보를 지속 | **고객 후기 요청**을 이어가기 |

바이럴 지표가 낮다는 것은 "우리가 글을 덜 썼다"가 아니라
**"고객이 우리 이야기를 덜 남겼다"** 는 뜻이다. 그래서 처방도 상담 품질과
후기 요청 습관으로 간다 — 매니저 실명이 후기에 남도록 요청하는 것이 대표적이다.

> 결국은 매장별 현황, 채널별 현황은 그 데이터가 서로 연동되어 있어."

```
        같은 자료
       ↙        ↘
  채널 축        매장 축
 (채널 타일)   (매장 대시보드)
```

- **채널 축** — 타일 하나 = 채널 하나. 그 채널 안에서 브랜드·품목·매장·담당자를 정리한다.
- **매장 축** — 매장 하나를 놓고 **채널마다 카드 하나**. 그 매장이 각 채널에서 어떻게 보이는지.

**새 채널을 붙일 때는 반드시 둘 다 만든다.** 하나만 만들면 화면이 갈라진다.

| 만들 것 | 어디 |
|---|---|
| 채널 데이터(두 축) | `scripts/build_{채널}_web.py` — `total/s/l/months/items` + `stores{매장: {s,l,mgr,last}}` |
| 히어로 타일 | `web/index.html` 의 `#sourceMosaic` + `data-go` 분기 |
| 채널 화면 | `web/{채널}-view.js` — `window.open{채널}()` |
| 매장 카드 | `web/store-scope.js` 의 `CHANNELS` 배열 + `{채널}Card()` |

**매장 이름은 `build_web_data.dept_store_of()` 를 재사용한다.** 채널마다 따로 뽑으면
같은 매장을 다른 이름으로 불러 두 화면이 어긋난다.

**표본 크기를 숨기지 않는다.** 제이웨딩 512건이 다이렉트웨딩 84,419건 옆에 같은 크기로
놓이면 같은 무게로 읽힌다. 화면에 "표본이 훨씬 작습니다"를 적고,
그 채널의 **강점**(제이웨딩은 매장·담당자 지목)에 무게를 두게 안내한다.

## 단위마다 묻는 것이 다르다 — 전국 / 도시 / 매장 (2026-08-23 사용자 지시)

> "전국, 도시, 매장별 페이지의 분석 내용과 분석의 밀도가 차이가 있어야 한다 …
> 전국은 좀 더 큰 시각에서, 매장의 경우 세밀한 부분까지."

실측해 보니 **도시 화면이 매장 화면의 축소판**이었다 — 같은 카드(품목·혜택·추이,
계약 규모·리스크)를 둘 다 쓰고 있었다. 단위만 다르고 시각은 같았던 셈이다.

| 단위 | 묻는 것 | 화면에 두는 것 |
|---|---|---|
| **전국** | 구조가 어떤가 | 전체 규모·지도 · 우위/열세를 만든 구조 · 품목 경쟁 지형 · 매니저 실명 · 몇 개점 우위 |
| **도시** | 어디쯤이고, 안에서 얼마나 갈리나 | 표본 순위·전국 대비 · **매장별 순위(주인공)** · 도시 안 격차 · 쏠림 · 전국과 다른 점 |
| **매장** | 무엇을 어떻게 할까 | 품목·혜택·추이 · 계약 규모 · 매니저 실명 · 현장 액션 · 후기 원문 |

**금지: 매장급 디테일(품목별 처방·객단가)을 도시에 두지 않는다.**
도시에서 그걸 보면 매장 목록이 눌린다 — 실제로 진단이 529px 을 먹어
매장 목록에 123px 만 남았고, 서울 20곳이 **행 높이 6px** 로 찌부러졌다.

### 공간은 주인공에게 준다

도시 화면의 주인공은 **매장 목록**이다. 실측으로 잡은 배분:
- 진단 `max-height: 54%`, 목록 `min-height: 170px`
- 매장 12곳 초과면 목록을 **2열**로(서울 20곳 → 행 높이 6px → 32px)
- 매장이 많은 도시는 진단을 **2줄**로, 적으면 3줄
- 기회 카드는 **걷어냈다** — 바로 옆 매장 목록이 같은 것을 더 자세히 보여준다(중복)

도시 액션은 한 수만 짚고 `→ 품목·혜택별 처방은 매장을 눌러 확인하세요` 로 넘긴다.

## 채널 줄에 무엇을 두는가 (2026-08-24 사용자 지적)

> "채널별 현황 페이지에서 혼수기반 바이럴 채널에 왜 네이버 리뷰가 있는거야?
> 네이버 리뷰는 혼수기반 바이럴이 아니야. 네이버 리뷰는 매장별 현황에서

**혼수 기반 바이럴 채널 = 혼수 준비 중에 오가는 가전 이야기.** 그것만 이 줄에 둔다.

| | 무엇 | 어디에 |
|---|---|---|
| **본류** | 웨딩카페 후기 — 다이렉트결혼준비 · 제이웨딩 · 블로그 · 맘카페 | 채널 줄 |

| **매장 평가** | 네이버 리뷰·예약 — 방문자 평가이지 혼수 후기가 아니다 | **매장별 현황에만** |

네이버 리뷰는 성격이 다르다. 매장 대시보드에서 **그 매장의 리뷰**를 보는 것이 제자리다
(카드를 누르면 그 매장 리뷰 상세로 들어간다). 채널 줄에 두면 혼수 바이럴 합계에
방문자 평가가 섞여 숫자의 뜻이 흐려진다.

**히어로의 '누적 N건 센싱'은 이 줄에 있는 타일의 합**이다 — 그래서 네이버 리뷰를 빼자
84,955건(혼수 채널만)이 됐다.

## 분석 화면은 인사이트로 끝나야 한다 (2026-08-24 사용자 지시)

> "분석된 페이지는 인사이트가 있어야해. 삼성스토어에서 참고할 만한 내용이 있어야 해.

| 표본이 작습니다 (그것만) | 매장명이 적힌 글 5곳이 **하이마트·LG가 올린 홍보** — 경쟁이 인스타로 고객을 부르고 있습니다 |

**판별법:** 승패가 뒤바뀌어도 같은 문장이 나온다면 그것은 인사이트가 아니다.

방법론 고지(표본 기준 추정치·예약 건수 외부 조회 불가 등)는 **여전히 필요하다**.
다만 그것'만' 남으면 안 된다. 화면마다 `현장 액션` 카드(`.yt-act`)를 둔다.

## 화면 이동은 브라우저에 맡긴다 (2026-08-24 사용자 지시)

> "페이지 이동 버튼은 이제 필요없는거 같아. 브라우저의 기능을 사용하게 됨에 따라"

화면 안의 `처음/뒤로/앞으로` 버튼(`VNAV.bar()`)은 **전부 걷어냈다.**
브라우저의 뒤로/앞으로가 같은 일을 하고, 그쪽이 사용자에게 이미 익숙하다.

**다만 `VNAV.push()` 는 그대로 둔다.** 이게 없으면 화면을 열어도 히스토리에
쌓이지 않아 뒤로가기가 **사이트를 떠나 버린다**. 버튼만 없앤 것이지
히스토리 연동을 없앤 것이 아니다.

새 화면을 만들 때: `VNAV.push({id, label, open})` 는 호출하고, `VNAV.bar()` 는 넣지 않는다.

## 기간 UI 는 `VPER.bar()` 를 쓴다 (2026-08-24)

사용자가 "유튜브·인스타에 기간 탭이 없다"고 했는데 **실은 있었다.**
`html()` 만 붙여 놓아 146px 짜리 칩 두 개가 화면 오른쪽 끝(x=1265)에 붙어 있었고,
다이렉트웨딩은 366px 에 현재 기간 라벨까지 있었다 — 같은 기능인데
눈에 띄는 정도가 달라 **없는 것처럼 보였다.**

`VPER.bar()` 를 쓰면 `현재 기간 라벨 + 칩` 이 함께 나와 무게가 같아진다.
새 화면은 `per().bar()` 를 쓴다. `html()` 은 라벨을 따로 그리는 화면에서만.

## 카드 상세 색 원칙 — 긍정 파랑·부정 빨강 (2026-08-25 사용자 지시)

> "카드를 클릭하고 들어가면 긍정내용은 파란색, 부정적 내용은 빨간색으로 기본 원칙으로 작성"

`<b class="warn">`가 부정을 표시하는 관례는 이미 있었지만, **컴포넌트마다 색을
따로 정의**해 짝(`.warn` 오버라이드)이 없는 곳이 있었다. 실측: `.ca-reasons li span b`,
`.fc-sec.tip p b`는 자기 색(파랑)만 있고 `.warn` 대응이 없어 "오븐 39%"(부정)가
파랗게 보였다.

**고친 법 — `web/cafe-analysis.css` 맨 끝에 한 번만 못박는다:**
```css
.ca2 .fc-dbody b.warn, .ca2 .ca-reasons b.warn, ... { color: #d23b54 !important; }
```
새 카드·새 문장을 추가할 때 `.warn` 클래스를 붙이기만 하면 어디서든 빨강이 이긴다 —
컴포넌트별로 `.warn` 대응 색을 또 정의할 필요가 없다. `!important`는 이 규칙에 한해
의도적으로 쓴다(전역 원칙이 개별 컴포넌트 색보다 항상 이겨야 하므로).

## 숫자를 나란히 붙이지 않는다 (2026-08-25)

`<i>82%</i><em>977</em>`처럼 단위 없는 숫자를 퍼센트 바로 뒤에 붙이면
"82%977"로 읽혀 무슨 값인지 알 수 없다. 반드시 **구분자(가운뎃점)와 단위**를 넣는다 —
`<em> · 977건</em>`. CSS `margin-left`만으로는 안 된다 — innerText·복사·스크린리더에
간격이 전달되지 않는다. 실제 공백 문자를 넣는다.

## 유튜브·인스타 검색어는 넓히면 늘어난다 (2026-08-25 실측)

가전 낱말이 든 검색어/해시태그를 8→26개(유튜브), 4→18개(인스타)로 늘렸더니
유튜브 54→97편, 인스타 69→176건으로 늘었다. **기간을 못 고르는 채널은 검색어 수가
곧 표본 크기다.** 검색어는 반드시 가전 낱말이나 제품명을 포함해야 한다 —
"혼수 준비" 같은 넓은 말만 쓰면 예식장·드레스가 끌려와 걸러내는 데만 힘이 든다.

## 기간을 바꿔도 안 변하는 카드 — 원인은 "고정 CD 값을 직접 읽음" (2026-08-25)

> "기간 설정에 따라 분석 내용이 달라야 하는데 일부 변동이 없는게 보여"

**매니저 실명 카드(`mgrCard()`)가 기간과 무관하게 완전히 고정**돼 있었다.
1월·8월·전체 모두 "21/50 · 전국 40%"로 동일. 원인: `CD.mgr`/`CD.mgrStore`
(빌드 시점 전체 기간 고정값)를 직접 읽고 있었다 — 다른 카드는 전부
`hasF() ? A() : CD` 패턴으로 선택 기간을 반영하는데 이 카드만 예외였다.

**정작 데이터는 이미 기간별로 만들어져 있었다.** `scripts/build_web_data.py`가
매니저 실명 언급을 날짜 인덱스 팩트 테이블(`nm_prepped`)로 이미 인코딩해 두었고,
`web/fact.js`의 `VFACT.agg()`가 이를 디코드해 `R.mgr`/`R.mgrStore`를 기간별로
정확히 만들어 내고 있었다(실측: 1월 삼성실명 522건 vs 8월 304건, 완전히 다름).
**빌드·디코드 인프라는 맞았는데 화면(cafe-analysis.js)만 그걸 안 쓰고 있었다.**

`lg` 카드("품목별 이탈 현황")의 "실명 후기(구조적 열세)" 문단도 같은 원인으로
`CD.mgr`를 직접 읽어 똑같이 고정돼 있었다.

**교훈 — 새 카드/블록을 만들 때:**
- 숫자를 넣기 전에 `hasF() ? A() : CD` (또는 `perData()`) 패턴을 쓰는지 확인한다.
- "왜 기간이 안 바뀌지"가 의심되면, 먼저 데이터가 애초에 기간별로 존재하는지
  (`window.VFACT.agg(start,end)`를 콘솔에서 직접 호출)를 확인한 뒤 화면 코드를 고친다 —
  데이터가 없어서인지 화면이 안 쓰고 있어서인지는 원인이 다르다.
- `grep -n "CD\.\w\+" web/cafe-analysis.js`로 `hasF()`/`perData()` 가드 없이
  `CD.*`를 직접 읽는 곳을 주기적으로 훑는다.
