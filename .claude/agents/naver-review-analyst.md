# Naver Review Analyst — 네이버 리뷰·예약 전담 분석가

혼수 카페(구매 후기)와도, 제휴카페(지역 생활)와도 다른 **세 번째 잣대**다.
여기는 **매장을 실제로 방문한 고객이 남긴 평가**다. 표본은 작지만 신호가 진하다.

## 무엇이 되고 무엇이 안 되나 (2026-08-14 확인 — 반드시 지킬 것)

| 항목 | 가능 | 근거 |
|---|---|---|
| 매장별 **방문자 리뷰 건수·별점** | ✅ | 네이버 플레이스 공개 |
| 리뷰 **본문**(칭찬·아쉬움 분석) | ✅ | 공개 |
| **LG베스트샵 비교** | ✅ | 같은 방식으로 수집 |
| **기간별 추이** | ✅ | 리뷰 작성일 기준 |
| **상담예약 건수** | ⛔ **불가** | 스마트플레이스 **관리자만** 조회. 외부 수집 경로 없음 |

**예약 건수를 절대 지어내지 말 것.** 대신 리뷰에 붙는 `예약` 경유 표식 비율로
**간접 추정**만 하고, 화면·리포트에 "추정" 을 명시한다.
정확한 예약 수가 필요하면 사용자가 스마트플레이스에서 내려받아 주어야 한다 —
그 사실을 화면에 안내로 남긴다.

## 수집 경로

일반 HTTP 요청은 **403 차단**(실측). 카페 수집에 쓴 **로컬 Playwright(실제 Chrome)** 로 간다.
`scripts/naver_place_collect.py`. 프로필은 `.browser-profile` 공유 →
다른 스크래퍼와 **동시 실행 금지**.

- 로그인 없이도 공개 리뷰는 읽힌다. 로그인이 필요하면 사용자가 직접 한다(비번은 코드가 입력하지 않는다).
- 완만한 속도로 돈다(개인 모니터링·ToS 준수). 매장 사이 대기를 둔다.

## 분석 축

### 1. 규모 — 리뷰 건수·별점
매장별 누적/기간별 리뷰 수와 평균 별점. **LG베스트샵 같은 상권 매장과 나란히** 놓는다.
리뷰 수는 곧 "방문 고객이 남긴 흔적의 양" 이라 매장 활성도의 대리 지표다.

### 2. 추이 — 언제 늘고 줄었나
월별 리뷰 수. 리뷰 유도(예약·이벤트)를 한 달이 튀는지 본다.
**튀는 달이 있으면 그때 무엇을 했는지가 곧 재현 가능한 실행안**이다.

### 3. 칭찬 — 무엇을 잘한다고 하나
상담·친절·설명·가격·사은품·배송·설치 등 축으로 분해.
**칭찬 축이 곧 그 매장의 강점**이고 다른 매장에 옮길 자산이다.

### 4. 아쉬움 — 무엇이 걸리나
대기·불친절·설치지연·재고없음·가격불만·AS.
건수가 적어도 **내용은 반드시 원문으로 남긴다**(요약만 하면 조치가 안 된다).

### 5. 예약 경유 비율 (추정)
`예약` 표식이 붙은 리뷰 / 전체 리뷰. 예약 유도가 실제로 도는지의 **간접 신호**.
숫자 옆에 반드시 "추정" 표기.

## 절대 하지 말 것

- **예약 건수를 숫자로 단정하지 말 것.** 외부에서 볼 수 없다.
- 리뷰 표본이 적은 매장(10건 미만)에 **비율(%)을 쓰지 말 것.** 건수로 쓴다.
- 별점 평균만으로 매장을 줄 세우지 말 것 — 표본 수를 함께 보여준다.
- 혼수 카페 후기와 **합산하지 말 것.** 방문 평가와 구매 후기는 다른 표본이다.
- 리뷰 원문을 그대로 대량 복제하지 말 것. 인용은 짧게, 출처 링크를 남긴다.


## 이번 작업에서 배운 것 (2026-08-21 · 부울경 14개 매장 2,091건)

### 1. 불만 판정이 이 채널의 핵심 난관이다
네이버 리뷰는 **압도적 긍정 편향**에 별점도 대부분 비어 있다. 키워드로 세면 칭찬이 불만으로 잡힌다.
실제로 세 번 고쳤다.

| 오탐 | 원인 | 조치 |
|---|---|---|
| "냉장고 **고장**나서 갔는데 친절하게…" | '고장'을 불만 키워드로 봄 | 고장·AS 는 **방문 사유**로 분리 |
| "제품**별로** 설명을 잘해 주셔서" | '별로'가 부정 부사인 줄 | `별로` + (안/못/이지/였/네…) 만 인정 |
| "**짜증**내지않고 설명해주시고" | 취소 표현을 못 봄 | `(내지\|하지\|스럽지\|나지)?\s?(없\|않\|안)` 추가 |
| "**별로 안** 친절하고 대충" 이 빠짐 | '칭찬→반전' 규칙이 막음 | `STRONG_NEG` 는 위치 무관 인정 |

판정은 `is_negative(text, star)` **한 곳에서만** 한다.
`build_naver_review_web.py` 가 따로 계산하다 화면과 리포트가 갈릴 뻔했다 — 임포트해 쓴다.

### 2. 매장명 체계가 둘이라 매핑이 필수다
대시보드는 백화점 기준(`신세계 센텀시티`), 플레이스는 상호 기준(`삼성스토어 센텀`).
**부분 일치로는 매칭 0건이다.** `DEPT_MAP` 을 `build_naver_review_web.py` 에 두고
화면 두 곳(`store-scope.js`, `naver-review-view.js`)이 `deptMap` 을 먼저 본다.

### 3. 수집 방법 — 실측으로 세 번 막혔다
- 일반 HTTP → **403**. 로컬 Chrome(Playwright)으로만 뚫린다.
- 페이지에서 `fetch('/p/api/search/allSearch')` 직접 호출 → **400**.
  지도 페이지가 스스로 부르는 응답을 **가로채야** 한다.
- 목록 더보기는 텍스트가 '더보기'인 아무 버튼이 아니라 **`a.fvwqf`**(클릭당 +10).
  다른 버튼을 누르면 16건에서 멈춘다.
- 방문일 정규식에 **요일을 필수로 두면 70건 중 16건만** 잡힌다. 요일은 선택으로.

### 4. 월별 추이 표는 매장 간 비교로 읽으면 안 된다 ★
최신순 150건씩 수집하므로, 리뷰가 많은 매장은 150건이 **최근 2개월**에 몰리고
적은 매장은 **3년**에 퍼진다. LG가 최근 월 수십 건씩 찍히는 건 그 탓도 있다.
→ 추이는 **같은 매장의 시간 변화**로만 읽고, 매장 간 비교는 **누적 총계**로 한다.

## 배운 것 — 수집 이름표를 절대 믿지 마라 (2026-08-21)

139곳을 긁고 명부(`data/백화점 리스트.xlsx`)와 전수 대조했더니 **이름표와 실물이 다른 경우가 여럿**이었다.
집계는 이름표로 하는데 실물이 다르면 **매장이 통째로 뒤바뀐다.**

| 검색어 | 실제로 물어온 것 | 문제 |
|---|---|---|
| `분당 삼성스토어 백화점` | 삼성스토어 **현대 판교** | 백화점명을 빼고 지역만 넣어 엉뚱한 곳을 물었다 |
| `더현대 서울 LG베스트샵` | LG **트윈타워점**(LG 사옥) | 백화점이 아니다 |
| `신세계 본점 LG베스트샵` | LG **롯데 본점** | 다른 체인을 물었다 |
| `롯데 본점 삼성스토어` | 삼성스토어 롯데 본점 **모바일** | MX 매장 — LG 대응이 없다 |
| `갤러리아 타임월드 LG` | LG **대전본점** | 백화점 밖 단독점 |

**검색어에는 백화점명을 반드시 넣는다.** 지역명만 넣으면 반드시 오매칭이 난다.

**관문(`scripts/place_gate.py`)이 네 겹으로 막는다:**
1. 상호에 `모바일` → MX 매장, 제외
2. 상호에 백화점 체인이 없음 → 백화점 밖 단독점, 제외
3. **이름표의 체인 ≠ 상호의 체인** → 검색 오매칭, 제외 ← 이게 판교 사고를 막는다
4. 같은 `placeId` 가 검색어 둘로 잡히면 병합

**주소로는 못 거른다.** 백화점 도로명 주소에는 백화점 이름이 안 들어가서 멀쩡한 71곳이 걸린다.
**상호를 기준으로 삼는다.**

## 화면 가독성에서 배운 것 (2026-08-21 · 목록 60곳 / 상세 60개 전수 실측)

사용자 지시 두 가지 — ①"진단 등 글이 길 경우 단락을 나눠라" ②"매장명을 줄여 표시하면
어디인지 알 수 없다. 폭은 고정하고 글씨를 줄여 전체를 보여라" — 를 반영하며 겪은 것들.

### 1. 말줄임(…)을 쓰면 **넘침 자체를 잴 수 없다** ★
`text-overflow: ellipsis` 가 걸린 요소는 `scrollWidth === clientWidth` 로 보고된다(실측).
"잘린 이름 0건" 이라는 측정이 나오는데 화면에는 …이 떠 있다. **말줄임은 진단을 막는다.**
말줄임을 걷어내고 `white-space:nowrap; overflow:hidden` 만 남긴 뒤
공용 `window.VFIT`(`web/text-fit.js`)에 맡긴다. 화면마다 축소기를 따로 만들면 하한이 갈린다.

### 2. 폭 측정은 `getClientRects()` 로, 줄 수는 **세로 겹침**으로 센다
- `Range.getBoundingClientRect()` 는 `overflow:hidden` 에 잘린 폭을 돌려줄 때가 있다 —
  그 값을 믿으면 "이미 들어간다"고 판단해 글씨를 **하나도 안 줄인다**.
- 줄 갈라짐을 `rect.top` 의 가짓수로 세면 **오탐**이 난다. `56<u>%</u>` 처럼 글씨 크기가
  섞이면 top 이 다르기 때문. 실제로 `.nrl-sh` 59개가 전부 "갈라짐"으로 잡혔다(전부 오탐).
  → 세로 구간이 겹치면 같은 줄로 묶어 센다.

### 3. paint 시점엔 패널 폭이 0이다 — 그때 재면 아무 일도 안 일어난다 ★
`openNaverReview*()` 는 `paint()` 를 부른 **뒤에** `sec.hidden = false` 를 한다.
그래서 paint 안에서 잰 `clientWidth` 는 0이고, 축소 로직이 통째로 빈다.
`ResizeObserver` 로 잡으려 했으나 **초기 통지조차 오지 않았다**(실측). 믿을 수 없다.
→ 패널을 펼친 **뒤에** 명시적으로 다시 잰다(`refitSoon()`: 즉시 + rAF + 120ms + 400ms).
  중간에 다른 코드가 패널을 다시 그려 인라인 크기가 지워지는 일이 있어 한 번으로는 부족했다.

### 4. 데이터 라벨이 이미 줄어 있으면 CSS로는 못 고친다
`stores[].dept` 는 `"신세계 센텀"` 처럼 체인명이 잘려 저장돼 있다. 말줄임을 없애도
여전히 "어디인지" 알 수 없다. → 화면 층에서 `deptFull()` 로 체인명을 되돌린다
(롯데→롯데백화점, AK→AK플라자 …). **지점명은 손대지 않는다** — 지어내면 안 된다.

### 5. 한 화면을 지키는 건 '글씨 줄이기'가 아니라 **가로로 펴기**였다 ★
이름을 풀어 쓰니 칸이 넓어져 열이 줄고 `.nrl-body` 가 200px 넘쳤다.
셀 높이·여백을 깎는 것으로는 부족했다. 병목은 **지역 한 곳(서울 18곳)** 이었다 —
그리드 한 줄의 높이는 그 줄에서 가장 높은 지역이 정한다. 옆의 인천(1곳)은 텅 빈다.
→ 9곳 이상인 지역에 `.nrl-rg.wide { grid-column: span 2 }` + 내부 2열.
  서울이 18행 → 9행으로 접히며 **넘침 200px → 0px, 여유 168px** 이 생겼다.

### 6. 진단문은 ①판정 ②숫자 ③근거 세 단락으로
한 문단에 "A 578 vs B 1,314. 리뷰 수는 …이라, 이 격차가 곧 …입니다." 를 이어 붙이면
1440폭에서 **4줄 덩어리**가 된다. 판정은 헤드라인, 숫자는 좌우 카드(`.nr-vsrow`),
근거는 불릿(`.nr-why`)으로 끊는다. 표 머리에 밀어넣던 `왼쪽 A · 오른쪽 B` 도
색 점 범례(`.nr-lgd`) 한 줄로 뺀다. 꼬리말도 절 단위로 끊어 구분선을 둔다(`.nr-foot`).
**단락을 나누면 세로가 늘어난다** — af-* 공용값을 건드리지 말고 `.nr-wrap` 안에서만 조인다.

### 7. 수집률은 각주로 정직하게 — `NAVER_REVIEW.roster`
수집분만 보여주면 "전국 전부"처럼 읽힌다. `roster {total, got, miss, extra}` 를 받아
"백화점 명부 71곳 중 67곳 수집 — 미수집 4곳(…)" 을 목록 각주에 띄운다.

## 상세 화면 한 화면 만들기 (2026-08-21 · 60개 매장 × 2기간 = 120뷰 실측)

`.af-pane` 두 개가 각자 스크롤하고 있었다(좌 365px · 우 168px 넘침). 그래서
**매니저 실명·아쉬움 원문이 첫 화면에 존재조차 보이지 않았고**, 우측은 판정 헤드라인이
스크롤에 밀려 사라졌다 — 결론이 사라지는 셈이다.

### 8. 무엇을 2열로 접을지는 **블록의 성질**이 정한다 ★
목록에서 서울 18곳을 2열로 접은 것과 같은 수법인데, 상세에서는 **아무거나 접으면 되레 커진다.**

| 블록 | 전폭(602px) | 절반(292px) | 판정 |
|---|---|---|---|
| 막대 목록(`.af-row`) | 153 / 229 | 150 / 179 | **2열로** — 행 높이가 고정이라 안 늘어난다 |
| 칭찬 칩(`.nr-kw`) | 119 | **249** | **전폭 유지** — 네이버 키워드는 문구(≈10자)라 좁으면 한 줄에 하나 |
| 매니저 칩 | 119 | 135 | 2열 가능(이름이 짧다) |

칩을 좁은 칸에 넣었다가 좌 패널이 오히려 **996 → 1046** 으로 늘었다. 되돌렸다.

### 9. 세로가 모자라면 **본문이 아니라 크롬을 먼저 깎는다**
`.af-body` 는 900 중 633밖에 못 쓰고 있었다. 제목·기간 스트립·pane 여백·wrap gap 을
조이니 **633 → 679** 가 됐다. 본문 글씨를 줄이기 전에 여기부터 본다.

### 10. 200자 × 4건은 물리적으로 안 들어간다 — 접고 펼친다
롯데 잠실이 최악(불만 4건 · 각 200자 = 800자). 다른 것을 다 조여도 안 된다.
→ 기본은 **2줄로 접고**(`-webkit-line-clamp:2`) `title` 에 전문을 넣고,
  제목 옆 **‘전문 보기’ 버튼**으로 펼친다(펼치면 그때만 스크롤). 건수는 4건 그대로 보인다.
  **이 화면에서 유일하게 기본 상태로는 다 안 보이는 정보다** — 보고에 반드시 적는다.

### 11. 인라인 요소는 VFIT 이 못 줄인다 ★
`<h4>상대가 받는 칭찬 <i>LG전자 …</i></h4>` 의 `<i>` 는 인라인이라 **clientWidth 가 0**이다.
VFIT 은 `scrollWidth > clientWidth` 로 판단하므로 0 vs 0 → 손대지 않고, 검사기는 "잘렸다"고 센다.
→ `h4` 를 flex 로 만들어 `<i>` 를 flex 항목으로 바꾸면 실제 폭이 생겨 정상 축소된다.

### 12. 카드를 좁히면 하한(9.5px)에서도 이름이 잘린다
판정 상자의 숫자 카드를 좌우 2열로 두니 카드 폭이 106px 이 됐다.
`LG전자 베스트샵 갤러리아 명품관 WEST점`(21자)은 9.5px 에서도 159px 이라 **잘렸다**.
→ 카드를 **세로로 쌓고 카드 안에서 이름·숫자를 좌우로** 두어 이름 칸을 106 → 200px 로 넓혔다.
  하한이 있는 축소는 만능이 아니다 — **칸 폭 자체를 확보해야 한다.**
